# Full-stack web development and review

## Scope and execution

Identify the requested behavior and whether this is development, read-only review, or debugging and repair. Inspect the existing worktree, project instructions, manifests, lockfiles, runtime configuration, entry points and relevant callers. Record actual language, framework, runtime and dependency versions when discoverable; otherwise mark them unknown. Map the relevant browser, API, server, data store, third-party and deployment boundaries. Select representative routes, roles and flows for broad reviews and state exclusions. A URL without server source or configuration does not establish server or database safety.

For new development, use the project's established stack and conventions where applicable. Translate the user's goal into observable behavior, identify consequential missing requirements, and make proportionate choices. Implement only authorized features and use the same evidence and verification principles on AI-generated and human-written code. For debugging, gather symptom and baseline evidence, trace the likely cause, and verify the fix and affected behavior. For review-only work do not modify project files.

## Inspect the applicable boundaries

Follow real data and control flows from input to output, including server-side validation, encoding, authentication, authorization and object ownership. Where relevant inspect session and token handling, cross-site request defenses, secrets, configuration, logging and personal-data exposure. Examine API contracts, input/error handling, third-party calls and timeouts. For data operations examine parameterization, transaction boundaries, concurrency, migrations, backups and recovery only where accessible and relevant. Inspect deployment configuration, dependency versions, build artifacts and public/private boundaries where available. Check failure paths, idempotency and retries where the actual flow requires them. These are review prompts, not claims that every project uses every component or that an inspection proves safety.

Use project-native tests, type checks, linters, builds and safe runtime checks appropriate to the detected stack; inspect commands for side effects before running them. Prefer focused regression tests for consequential fixes and key behavior. Record exact checks and results, including missing tooling or environments. Do not run real payments, orders, messages, destructive actions, production exploits or migrations without appropriate explicit authorization and a safe test environment; otherwise mark the flow unverified. Never expose secret values or personal data in reports.

## Fact-check and applicability

Use code, configuration, safe execution, tests and observations as evidence of project behavior. Separately verify consequential normative, compatibility, security and currency claims against current primary sources: the applicable standard and provision, relevant Korean government or public-agency material, and official language, framework, platform or vendor documentation for the actual version. OWASP guidance can support security recommendations; identify guidance as guidance. Select sources for the issue and jurisdiction instead of forcing a fixed checklist or assuming every domestic public-sector rule applies to every site.

Open the specific source rather than relying on memory, a search snippet or a stale link. Record the source URL, section or version, check date, applicability and material exceptions next to the claim. Distinguish legal obligations, standards requirements, recommendations, project policy and preferences; do not infer legal applicability without facts. A standard describes an expected rule; it does not prove this implementation violates it. If browsing, a source, version or applicability cannot be verified, label that claim UNVERIFIED and explain what is missing; do not invent a citation, rule or compliance conclusion. Never present a limited review as security, accessibility or legal certification.

## Findings and handoff

Lead with a plain-language summary of user impact and the next action. Separate evidence-backed must-fix issues, confirmed defects, plausible risks, optional improvements and unverified items. Report verified strengths and concrete behaviors to preserve with their evidence, relevant criterion and scope; if none can be verified, say so. Apply the claim and numerical evidence audit in `evidence-and-severity.md`. For each actionable item give the trigger, file and line or observed evidence, actual versus uncertain impact, recommendation and relevant source with applicability. Record inspected components, roles, routes, checks, skipped items, remaining risks and, for authorized changes, what changed and how it was verified. Give technical detail in an appendix when helpful to a developer; do not bury the non-developer summary.
