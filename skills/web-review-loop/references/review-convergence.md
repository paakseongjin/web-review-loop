# Review convergence and feedback loop

Adapted to this skill from the Claude Code team's account of review convergence: https://claude.dev/blog/solving-code-review-at-anthropic/ (published 2026-10-15). That team's filters and outcomes are specific to its environment; this skill does not assume its tools, multiple agents, approval policy or performance results are available here.

## Establish the baseline

Define the requested scope, expected behavior, acceptance checks, boundaries, and risk before reviewing. Inspect project instructions and any applicable owner-written REVIEW.md, if present; honor its scope when consistent with the request. Record the starting revision and existing staged, unstaged and untracked changes where Git exists; distinguish the user's pre-existing changes from changes made in this session. Establish a safe, inspectable baseline of relevant contents and check results without committing, stashing, resetting or overwriting anything. If a revision or baseline is unavailable, record that limitation; do not claim an issue was introduced by the change without evidence. Read-only reviews can keep the ledger in context and final output; do not write a log file unless requested or otherwise authorized.

## Verify and triage candidates

Review the scoped diff against its intent and relevant callers, and inspect higher-risk boundaries proportionately. Verify each candidate with code and, when feasible and safe, a focused test or reproduction; actively look for counterevidence, existing validation, applicable framework behavior and intended design. Distinguish a proven defect, an unverified but consequential risk, an optional suggestion, and a false positive. Identify its trigger, impact, evidence and confidence. A style preference, naming choice, hypothetical edge case without meaningful impact, or alternative implementation is not a blocking defect. Do not suppress substantiated security, accessibility or correctness issues because of this filter. Check the baseline before assigning origin: introduced, pre-existing, or unknown. A pre-existing issue made materially worse or newly reachable by the change must be reported with that causal connection. An important pre-existing issue is reported separately, not blamed on the current change, and is not fixed outside authorized scope.

Use one stable ID for the same root cause and affected behavior even if file lines move. Group instances of the same failure class and inspect related instances inside the authorized scope, instead of repeatedly rediscovering one line at a time. Maintain a ledger of each finding, evidence, origin, disposition (open, fixed and verified, rejected with rationale, deferred, blocked, or unverified), and any relevant verification. An intentional and acceptable tradeoff can be rejected or deferred with a reason; never silently suppress it. Do not re-report a resolved, rejected or deferred item unless new evidence or a changed requirement invalidates its rationale; explain the new evidence when reopening. A related but distinct regression is a new finding linked to the prior fix.

## Run bounded fix and re-review rounds

A round is one scoped review of a particular code state, followed, when authorized, by a coherent batch of fixes and verification. Round 1 reviews the original requested scope. By default use at most three rounds total for this loop, including round 1; do not automatically use all three. After each batch, including the last allowed round, perform focused verification of that batch; this is part of the same round, not a new general review round. Compare the immediately previous reviewed state to the current state, verify the addressed findings and changed behavior, and inspect the new diff plus relevant affected callers, contracts and high-risk paths. Retain the original baseline and ledger for origin and regressions. For non-Git projects use an inspectable before/after comparison; if unavailable, mark re-review coverage unverified. Do not expand into another full-project audit merely to find more suggestions. Follow the user's explicit round limit if supplied; a limit does not authorize a false pass.

Before fixing, decide what must remain true and choose the smallest effective change. Inspect the whole related failure class within scope, then run relevant focused regression checks and affected project gates. Compare to baseline, document new failures separately from pre-existing failures, and check that the fix did not introduce another defect. A per-finding cap of three distinct attempted fixes is separate from the total round cap; whichever limit is reached first stops that activity. Avoid oscillation: do not revert and reapply competing designs without new evidence. Preserve user changes and safely undo only your own unsuccessful work when appropriate.

Stop successfully when requested acceptance criteria are met, actionable in-scope findings are addressed or explicitly resolved, relevant checks have actually passed, and re-review of the latest change finds no unresolved material regression. If no checks can be run, do not label them passed or declare the work fully verified. At the round cap, or when no safe useful next step exists, stop the automatic loop, reconsider the approach, and report unresolved items, risks, checks and next action; do not mark them fixed or pass. Continue independent in-scope work where safe without silently starting a fresh review loop to evade the limit. A newly discovered material security, safety or functional problem must be reported even after the cap: preserve the evidence, do not ship or claim success, and do not conceal it as a duplicate or an old finding. If within the authorized task and safe to act, address an urgent regression without restarting broad review; otherwise clearly explain what blocks completion. Risky changes and required human approvals remain subject to the project's actual rules; AI review is not a substitute.

## Reporting and learning

Report round count and stop reason; baseline and latest reviewed scope; findings with origin and disposition; tests run and skipped; confirmed regressions and remaining uncertainty. State when no actionable finding was found in the inspected scope. Report useful verified strengths and behaviors preserved without inventing praise. Keep minor optional suggestions separate and do not turn them into another fix cycle. For recurring false positives or missed defects, propose a precise project instruction or deterministic check and capture an anonymized evaluation case only when authorized; do not alter project policy, CI, or reviewer settings merely because a loop ran. Compare future reviewer changes against both known defects and clean cases; measure outcomes only when actual data exists.
