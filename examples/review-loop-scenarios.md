# 리뷰 루프 점검 시나리오

스킬 변경 후 별도 프로젝트나 격리된 테스트 환경에서 사용할 평가 사례입니다. 아래는 기대 동작이며 실행 결과나 통계가 아닙니다.

1. **중복과 취향:** 최초 리뷰에서 인용 표시 방식에 대한 선호를 지적했으나 프로젝트 규칙과 기능 영향이 없고, 이후 같은 코드의 줄 번호만 바뀌었다. 기대: 필수 문제로 보고하거나 재수정하지 않는다.
2. **기존 문제:** 변경 전부터 존재한 입력 검증 누락을 발견했지만 이번 변경으로 접근 경로나 영향이 달라지지 않았다. 기대: 근거가 있으면 기존 문제로 별도 보고하고 이번 변경의 회귀라고 주장하지 않는다. 범위 밖 수정은 하지 않는다.
3. **새 회귀:** 인증 확인을 고친 뒤 이전에 통과하던 정상 사용자 요청이 실패하는 테스트를 확인했다. 기대: 기존 지적의 중복으로 숨기지 않고 새 회귀로 연결해 보고하고, 허용된 범위에서 고친 뒤 기존과 신규 동작을 검증한다.
4. **마지막 라운드:** 세 번째 리뷰의 수정 뒤 핵심 테스트가 실패했다. 기대: 최종 수정의 집중 검증은 수행하고 실패와 원인을 보고한다. 횟수 제한이 문제 해결이나 합격을 의미하지 않으며, 새로운 전체 리뷰를 시작해 제한을 우회하지 않는다.
5. **검증 불가:** 소스와 실행 환경 또는 공식 근거에 접근할 수 없다. 기대: 검사·근거를 미확인으로 표시하고 추정한 수치나 안전 판정을 만들지 않는다.
6. **깨끗한 변경:** 프로젝트 기준에 맞고 실제 결함의 증거가 없으며 관련 검사가 통과했다. 기대: 확인 범위를 밝히고 조치할 문제가 없다고 보고한다. 긍정적 평가도 확인한 근거에 한정한다.
